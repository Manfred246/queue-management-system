# Система управления очередью

Приложение для организации обслуживания посетителей.
В ПР5 добавлен веб-интерфейс на Django 5.2, в ПР6 он переведён на шаблоны.
Посетитель выбирает услугу и получает талон. Сотрудник вызывает следующего
посетителя и завершает обслуживание.

## Целевая аудитория

- посетители организаций с электронной очередью;
- сотрудники, обслуживающие посетителей;
- администраторы, управляющие услугами и очередями.

## Возможности

- просмотр, поиск, отбор и сортировка услуг;
- добавление услуги и связанной с ней очереди;
- добавление и просмотр пользователей;
- открытие и закрытие очереди, изменение доступности услуги;
- выдача талона с номером, временем выдачи и оценкой ожидания;
- вызов следующего посетителя, отмена талона и завершение обслуживания;
- просмотр истории талонов;
- сохранение данных в JSON и восстановление при запуске.

## Основные сущности

| Класс | Основные атрибуты | Основные методы |
| --- | --- | --- |
| `User` | id, name, role | `can_receive_ticket`, `__str__` |
| `Service` | id, name, average_service_time, is_available | `set_available`, `__str__` |
| `Queue` | id, name, service, prefix, is_open, last_ticket_number | `set_open`, `can_issue_ticket`, `active_tickets`, `call_next`, `__str__` |
| `Ticket` | id, number, user, service, queue, status, issued_at | `cancel`, `call`, `complete`, `position`, `wait_time`, `status_text`, `__str__` |

У каждого класса есть конструктор `__init__`. Очередь хранит ссылку на услугу,
а талон связывает пользователя, услугу и очередь. Коллекции содержат объекты
этих классов. При загрузке JSON ссылки восстанавливаются по ID.

Статус талона, открытость очереди, счётчик номеров и доступность услуги
читаются через свойства `@property`, а изменяются методами с проверками.
Метод `__str__` задаёт представление каждого объекта для вывода.
Наследование для текущих сущностей не требуется.

## Правила работы

Одна очередь обслуживает одну услугу. Посетители вызываются по возрастанию
номеров талонов. В очереди может быть только один вызванный посетитель.
У посетителя может быть один активный талон в каждой очереди.
Сотрудникам талоны не выдаются. Роли хранятся как данные; входа в систему пока нет.

Статусы талона: `waiting`, `called`, `completed`, `cancelled`.
Отменить можно ожидающий или вызванный талон, завершить — только вызванный.
Отменённые талоны остаются в истории, их номера не используются повторно.

Закрытие очереди или отключение услуги запрещает выдачу новых талонов.
Обслуживание уже выданных талонов продолжается.
Оценка ожидания — число активных талонов впереди, умноженное на среднее время
услуги. Для вызванного посетителя учитывается полное среднее время обслуживания.

## Структура проекта

- `main.py` — меню и вывод данных;
- `users.py` — класс пользователя и добавление пользователей;
- `services.py` — класс услуги, добавление, поиск, отбор и сортировка;
- `queues.py` — класс очереди и добавление очередей;
- `tickets.py` — класс талона, выдача и поиск талонов;

- `utils.py` — проверка значений и консольный ввод;
- `data/state.json` — данные приложения;
- `tests/` — автоматизированные тесты;
- `requirements.txt`, `pytest.ini`, `.flake8` — зависимости и настройки проверок.

## Запуск и проверки

Требуется Python 3.10 или новее. Веб-версия использует Django 5.2.
`pytest` и `flake8` нужны для проверки проекта.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python main.py
```

В Windows используйте `python -m venv .venv` и активируйте окружение командой
`.venv\Scripts\Activate.ps1` в PowerShell.

Проверки из корня проекта:

```bash
python -m pytest -v
python -m flake8 .
```

Тесты проверяют методы классов, поиск и отбор услуг, порядок вызова,
переходы статусов, загрузку и сохранение JSON, обработку ошибок и меню.

## Веб-интерфейс ПР7

В репозитории есть заполненная база `data/queue.sqlite`. Для создания базы
в новой копии без этого файла выполните команды ниже. Импорт предназначен
для пустых таблиц; для существующей заполненной базы повторять его не нужно.
Встроенные миграции относятся только к служебной базе Django:

```bash
python manage.py migrate
python -m db.database
python -m db.import_json
python manage.py check
python manage.py runserver
```

Откройте http://127.0.0.1:8000/ в браузере.

| Страница | URL |
| --- | --- |
| Главная | `/` |
| Услуги и карточка услуги | `/services/`, `/services/1/` |
| Очереди и карточка очереди | `/queues/`, `/queues/1/` |
| Талоны и карточка талона | `/tickets/`, `/tickets/1/` |
| Доступные очереди для посетителя | `/queues/available/?user_id=1` |
| Статистика нагрузки | `/tickets/statistics/` |

Конфигурация Django находится в `queue_site/`. Созданы три приложения:
`homepage` — главная страница, обработчик 404 и статические файлы;
`catalog` — услуги и связанные с ними очереди;
`ticket_pages` — талоны и сведения об их посетителях.
Отдельное приложение пользователей пока не требуется: страницы регистрации
и входа относятся к следующим работам. Класс `User` ПР3 сохранён.

View-функции получают данные из `data/queue.sqlite` через стандартный
модуль `sqlite3`. Соединение задаёт `row_factory = sqlite3.Row`, поэтому
поля доступны по именам. SQL-запросы используют параметры `?`; соединения
закрываются в `finally`. Django ORM для предметной области не используется.
Веб-страницы показывают данные; выдача и обслуживание талонов выполняются
в прежнем консольном меню, которое продолжает работать с JSON.

HTML находится в Django-шаблонах. Представления подготавливают контекст и
вызывают `render()`. Функция `page()` удалена. Общая структура сайта находится
в `templates/base.html`, навигация — в `templates/includes/navigation.html`.
Дочерние страницы используют `extends` и блоки `title`, `content`.

Шаблоны приложений:

- `homepage/templates/homepage/index.html` — главная;
- `catalog/templates/catalog/service_list.html`, `service_detail.html` — услуги;
- `catalog/templates/catalog/queue_list.html`, `queue_detail.html` — очереди;
- `catalog/templates/catalog/includes/service_card.html` — карточка услуги;
- `ticket_pages/templates/ticket_pages/ticket_list.html`, `ticket_detail.html` — талоны;
- `ticket_pages/templates/ticket_pages/includes/ticket_status.html` — статус талона;
- `templates/404.html` — общая страница ошибки.

В `queue_site/settings.py` параметр `DIRS` указывает на общий каталог `templates`,
а `APP_DIRS=True` включает поиск шаблонов приложений.
Списки выводятся циклами `for` с веткой `empty`. Условия `if` показывают статусы
и сообщения об отсутствующих объектах. Фильтры `length`, `default` и `date`
используются для количества записей, названий и времени выдачи талонов.
Вывод значений через `{{ ... }}` автоматически экранируется Django.

Ссылки формируются через тег `url`. Пространства имён: `homepage`, `catalog`,
`queues` и `tickets`. Например, `catalog:service_detail` получает ID услуги,
а `tickets:ticket_detail` — ID талона. Адреса страниц ПР5 сохранены.

Оформление использует Bootstrap 5.3.3 через CDN и собственный файл
`homepage/static/homepage/css/style.css`. Логотип талона находится в
`homepage/static/homepage/img/logo.svg`. Файл `homepage/static/homepage/js/main.js`
подставляет текущий год в подвал. Все ресурсы подключаются тегом `static`.
Для загрузки Bootstrap нужен интернет. Django ORM пока не используется.

Проверка статических файлов:

```bash
python manage.py findstatic homepage/css/style.css
python manage.py findstatic homepage/img/logo.svg
python manage.py findstatic homepage/js/main.js
```
Служебная база `db.sqlite3` создаётся командой `migrate` и не хранится в Git.
Отдельная база предметной области `data/queue.sqlite` включена в репозиторий.

Для отсутствующего ID view передаёт `None` в шаблон и задаёт статус 404.
Шаблон показывает сообщение через ветку `else`. Неизвестный URL
обрабатывает `homepage.views.page_not_found`, подключённый через `handler404`
в корневом `queue_site/urls.py`. Для проверки общей страницы 404 временно
установите `DEBUG = False` в `queue_site/settings.py` и откройте `/nonexistent/`.
В `ALLOWED_HOSTS` указаны `localhost` и `127.0.0.1`.
После проверки верните `DEBUG = True` для локальной разработки.

В `data/state.json` есть демонстрационные посетитель Анна и талон A25.
Они перенесены в SQLite; карточка доступна по адресу `/tickets/1/`.
После ПР7 изменения через консольное меню остаются в JSON. Для нового импорта
сохраните существующую SQLite-базу отдельно и создайте новую пустую базу.
Автоматической синхронизации JSON и SQLite нет.

## База данных ПР7

Файлы: `sql/schema.sql` — создание таблиц, `sql/queries.sql` — 15 запросов
с назначением и примерами параметров, `db/database.py` — подключение и создание
таблиц, `db/import_json.py` — однократный импорт из `data/state.json`.
Путь к базе абсолютный и вычисляется относительно корня проекта.

| Таблица | Поля и типы |
| --- | --- |
| `users` | `id INTEGER PRIMARY KEY`, `name TEXT`, `role TEXT` |
| `services` | `id INTEGER PRIMARY KEY`, `name TEXT`, `average_service_time INTEGER`, `is_available INTEGER` |
| `queues` | `id INTEGER PRIMARY KEY`, `name TEXT`, `service_id INTEGER`, `prefix TEXT`, `is_open INTEGER`, `last_ticket_number INTEGER` |
| `tickets` | `id INTEGER PRIMARY KEY`, `number INTEGER`, `user_id INTEGER`, `service_id INTEGER`, `queue_id INTEGER`, `status TEXT`, `issued_at TEXT` |

Все поля обязательны: отсутствие значения для текущих сущностей не требуется.
Логические значения хранятся как 0 или 1, дата выдачи — как текст ISO 8601.
`DEFAULT` задаёт открытость очереди, доступность услуги, начальный счётчик
и статус талона. `CHECK` ограничивает статусы, роли и допустимые значения.
Пара `queue_id, number` уникальна.

Внешние ключи: `queues.service_id → services.id`, `tickets.user_id → users.id`,
`tickets.service_id → services.id`, `tickets.queue_id → queues.id`.
У пользователя, услуги и очереди может быть несколько талонов.
`PRAGMA foreign_keys = ON` включается для каждого соединения.

Сначала импортируются пользователи и услуги, затем очереди, затем талоны.
`executemany()` вставляет записи с параметрами `?`, bool преобразуется в int.
Импорт выполняется одной транзакцией: `commit()` сохраняет все записи,
`rollback()` отменяет вставки при ошибке. Повторный импорт в заполненные таблицы
завершается ошибкой ключа без удаления или изменения существующих данных.
Схему `python -m db.database` можно выполнять повторно: используется
`CREATE TABLE IF NOT EXISTS`.

Сценарии веб-части:

- Услуги: полный список и поиск по максимальному времени обслуживания,
  например `/services/?max_minutes=7`.
- Очереди и карточки: связанные названия услуг, доступность выдачи и нагрузка.
- Талоны: по умолчанию активные (`waiting`, `called`), вся история
  `/tickets/?state=all` или отменённые `/tickets/?state=cancelled`.
- Доступные очереди: посетитель вводит свой ID. Запрос исключает очереди с его
  активным талоном и оставляет открытые очереди доступных услуг. Это адаптация
  поиска свободных помещений из примера методички к правилам электронной очереди.
- Статистика: число активных талонов, среднее время доступных услуг, количество
  активных талонов по очередям и услугам. `LEFT JOIN` сохраняет нулевые группы,
  `HAVING` отбирает очереди по минимальной нагрузке, например
  `/tickets/statistics/?min_count=1`.

15 запросов в `sql/queries.sql` используются представлениями. Среди них есть
два списка, несколько фильтров `WHERE` и соединений `JOIN`, два отдельных
агрегатных запроса (`COUNT`, `AVG`), две группировки `GROUP BY`, `HAVING`
и подзапрос поиска доступных очередей. Карточка талона рассчитывает ожидание
по числу активных талонов впереди, как в консольной части.

Проверка в SQLite CLI из корня проекта:

```bash
sqlite3 -header -column data/queue.sqlite
```

В консоли `.tables` показывает таблицы, `.schema` — схему.
Для запуска всех запросов из файла задайте параметры. Для диагностики
`?1 = 1` подходит всем запросам с одним числовым параметром и даёт выборку
талонов со всеми фильтрами выключенными; список талонов лучше проверять
отдельно со строкой `active`, как в примере ниже:

```sql
.parameter init
.parameter set ?1 1
.parameter set ?2 1
.parameter set ?3 1
.read sql/queries.sql
.parameter set ?1 active
.parameter set ?2 active
.parameter set ?3 active
SELECT id, status FROM tickets
WHERE ?1 = 'all' OR (?2 = 'active' AND status IN ('waiting', 'called'))
   OR (?3 = 'cancelled' AND status = 'cancelled');
```

Имена таблиц и полей сверяйте со схемой. Пустая выборка корректна и обрабатывается
в шаблоне через `empty`; ошибочное имя столбца вызывает `OperationalError`.
Тесты SQL-части работают с временными базами и проверяют перенос, откат импорта,
внешние ключи, фильтры, статистику, ожидание и ответы 404.

## Хранение данных

JSON содержит четыре списка: `users`, `services`, `queues`, `tickets`.
Связи записаны в полях `user_id`, `service_id`, `queue_id`, а время выдачи —
в строке `issued_at` в формате ISO 8601. После загрузки создаются объекты классов.
Формат данных ПР2 сохранён.

Данные сохраняются после каждого успешного изменения. Перед изменением меню
создаёт копию состояния. Если операция или запись не удалась, рабочие данные
остаются прежними. Файл сначала записывается с расширением `.tmp`, затем
заменяет основной файл.

Если файла нет, используются начальные данные. Если JSON повреждён,
программа сообщает об ошибке и завершает запуск, сохраняя файл для исправления.
Путь к данным определяется относительно проекта. Одновременно следует
запускать только один экземпляр программы.
