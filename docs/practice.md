# Анализ и выполнение индивидуального проекта

## Источники требований

Перед доработкой изучены ПР1, ПР2 и ПР3. ПР1 задаёт исходный сценарий,
ПР2 — функциональную модель, ПР3 — преобразование этой модели в объекты.
Основные требования: ПР2, разделы 6.1–6.3 (страницы 11–26);
ПР3, разделы 5.1–5.6 (страницы 9–44).
Пример бронирования помещений адаптирован к предметной области очередей.
Учебные упражнения Яндекс Практикума, согласование темы и персональный отчёт
не относятся к доработке репозитория и здесь не отмечаются как выполненные.

## Исходный код ПР1

В `main.py` были четыре функции: проверка выдачи, следующий номер талона,
расчёт ожидания и текстовый статус. Данные задавались отдельными переменными.
Программа выдавала один талон A25 без сохранения, запрашивала количество
людей вручную и завершалась с ошибкой при нечисловом вводе.
Импорт `main.py` сразу запускал интерактивный сценарий.

Предметные ограничения: услуга определяет длительность обслуживания,
очередь определяет порядок вызова, пользователь получает талон,
талон связывает все три сущности и хранит состояние обслуживания.

## ПР2: выполненная функциональная модель

| Требование | Реализация |
| --- | --- |
| Преемственность ПР1 | Четыре функции перенесены в `tickets.py`; сохранён сценарий получения талона |
| Коллекции | Словари пользователей, услуг и очередей; список словарей талонов |
| Циклы | Меню, просмотр, поиск талонов и проверка записей JSON |
| Обработка коллекций | Добавление, поиск, отбор и сортировка услуг |
| Модули | `users`, `services`, `queues`, `tickets`, `storage`, `validation`, `utils` |
| Исключения | Повтор ввода, ошибки операций, загрузки и сохранения |
| JSON и контекстные менеджеры | `load_state`, `save_state`, проверка связей и атомарная запись |
| Типы и документирование | Аннотации и docstring основных функций |
| Первичные тесты | 33 тестовых сценария pytest |
| Стиль | flake8 без замечаний |
| Документация | Описание меню, модулей, JSON, установки и проверок в README |

Проверены все пункты меню, перезапуск с сохранёнными данными, неверный ввод,
неизвестные ID, повторный префикс, ошибки сохранения. Реальный запуск из
другого каталога подтвердил корректный путь к данным. В `pdb` поставлена
точка останова на формирование номера в `issue_ticket`, просмотрены значения
пользователя и счётчика, выполнен шаг: счётчик 24 даёт номер 25.
Неверный переход завершения ожидающего талона воспроизводится отдельным тестом
и отклоняется до изменения состояния.

## Анализ модели перед ПР3

| Будущий класс | Атрибуты | Поведение отдельного объекта |
| --- | --- | --- |
| `User` | id, name, role | Проверка роли, строковое представление |
| `Service` | id, name, average_service_time, is_available | Изменение доступности, строковое представление |
| `Queue` | id, name, service, prefix, is_open, last_ticket_number | Проверка выдачи, изменение открытости, следующий номер, порядок активных талонов |
| `Ticket` | id, number, user, service, queue, issued_at, status | Отмена, вызов, завершение, позиция, ожидание, строковое представление |

`Queue` будет хранить ссылку на `Service`. `Ticket` будет хранить ссылки
на те же экземпляры `User`, `Service`, `Queue`, которые находятся в коллекциях.
В JSON сохраняются идентификаторы; при загрузке сначала создаются пользователи
и услуги, затем очереди и талоны. Формат JSON ПР2 сохраняется.

Операции поиска, добавления в коллекцию, сортировки, загрузки/сохранения,
консольного ввода и вычисления общей формулы ожидания остаются функциями.
Изменения статуса талона и состояния очереди/услуги переходят в методы.
Композиция отражает предметные связи. Наследование не требуется:
посетитель и сотрудник отличаются ролью, но не поведением на текущем этапе.
Полиморфизм можно показать общим вызовом `str()` для разных сущностей.
Инкапсуляция нужна для управления допустимыми переходами статуса талона.

Контрольная точка перед ПР3 — коммит с выполненной и проверенной ПР2.
